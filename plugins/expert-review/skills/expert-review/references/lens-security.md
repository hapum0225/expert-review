# 렌즈: 보안 — Supabase 포함 (약자 S) v0.2

> 시험 상태: **정답 시험 없음** — 비공개 실제 프로젝트 1회 검토에서 출력 형식 · 안전 규칙이 지켜진 것만 확인했다(2026-10-15). 결과는 더 조심해서 읽는다.
> 근거: 2026-10-15 웹에서 열어 확인한 공식 자료 36건(Supabase · Next.js · Vercel · PostgreSQL · OWASP Top 10:2025 · OWASP ASVS 5.0 · OWASP API Top 10 · 행정안전부 「소프트웨어 개발보안 가이드」(2021.11) 구현 단계 49항 대조) — 항목별 근거와 49항 대조표는 `lens-security-sources.md`. 49항 목록은 행안부 원문 PDF를 열지 못해 2차 자료를 교차 점검한 것이다. iron-laws(공개 규칙 모음)는 규칙 이름 · 분류만 참고했고 그 판정은 쓰지 않았다.
> 등급: 확립 = 공식 문서 · 표준(ASVS는 L1~L3) / 방향성 = 연구 · 관행 / 추정 = 근거가 약한 것. **출처 규칙(2026-10-22)**: 공식 문서 · 표준 · 법령이 아닌 한 출처(한 사람 · 한 영상 · 한 글)에서만 나온 기준은 '추정'으로 두고 판정 근거로 쓰지 않는다. 출처끼리 엇갈리면 하나로 합치지 않고 그 항목에 양쪽을 나란히 적는다.
> 보는 대상: `supabase/migrations` · SQL, `app/**`(page · route.ts · 서버 액션), `proxy.ts`/`middleware.ts`, `.gitignore`, `package.json` + 락파일, `vercel.json`, `supabase/config.toml`(있으면). `.env*`는 내용을 열지 않는다(이름 · 존재만).

| 항목 | 예/아니오로 물을 것 | 등급 |
|---|---|---|
| S1 행 수준 보안(RLS) | API에 노출되는 스키마(보통 public)의 `create table`마다 `enable row level security`가 있는가(없는 테이블 목록). `disable row level security`는 없는가. 뷰는 `security_invoker = true`이거나 노출 스키마 밖인가 | 확립 |
| S2 정책 내용 | 정책이 소유자(`auth.uid()`)나 역할로 좁히는가. `using (true)` · `with check (true)` · `to anon` 쓰기 정책은 없는가. insert엔 `with check`, update엔 `using`과 `with check`가 둘 다 있는가. 정책 조건이 사용자가 고칠 수 있는 `user_metadata`를 참조하지 않는가 | 확립 |
| S3 서비스 키 | service_role/secret 키(`SUPABASE_SERVICE_ROLE_KEY` · `SUPABASE_SECRET_KEY` · 접두 `sb_secret_`)가 `NEXT_PUBLIC_` 변수 · `'use client'` 파일과 그 파일이 가져오는 모듈에 닿지 않는가(값은 보지 않는다). 그 키로 만든 클라이언트는 호출자 확인(S4)을 마친 서버 코드에서만 쓰는가 | 확립 |
| S4 서버 쪽 권한 확인 | 서버 액션 · route.ts · RPC마다 (a) 로그인 확인이 그 함수 안에 있는가(페이지 가드에 기대지 않음) (b) 서버에서 검증된 신원(`getClaims()` / `getUser()`)을 쓰는가 — `getSession()` 단독은 쿠키 위조에 열려 있다 (c) 대상 자원의 소유 · 권한을 확인하는가 (d) 클라이언트가 보낸 userId · role · 금액을 믿지 않는가 | 확립 |
| S5 SECURITY DEFINER 함수 | 함수마다 `set search_path`가 고정(빈 문자열, 또는 신뢰 스키마 뒤 `pg_temp` 마지막)이고 본문이 스키마 접두어를 쓰는가. 함수 안에서 호출자 소유를 확인하는가. `revoke execute ... from public`/`anon` 뒤 필요한 롤에만 `grant execute`가 있는가 | 확립 |
| S6 관리자 기능 | 관리자 판정 근거가 서버 · DB에서 사용자가 고칠 수 없는 값인가(쿼리스트링 · 쿠키값 · 클라이언트 상태 · `user_metadata` 아님). 관리자 서버 액션 · route · RPC가 각자 권한을 다시 확인하는가 | 확립(서버 강제) · 방향성(다층 보강) |
| S7 입력 검증 · 주입 | SQL · RPC 호출이 매개변수화돼 있고 문자열 이어붙이기가 없는가. 동적 정렬 · 컬럼 · 테이블명은 허용 목록인가. `dangerouslySetInnerHTML`/`innerHTML`에 정제 안 된 사용자 데이터가 들어가지 않는가. 서버 액션 · route 입력을 서버에서 스키마로 검증하는가(`[param]` 포함). Supabase `.or()`/`.filter()`에 사용자 문자열을 그대로 끼우지 않는가 | 확립 · 방향성(`.or()` 필터) |
| S8 인증 흐름 | 로그인 뒤 이동 주소(`next` · `redirectTo`)가 같은 사이트 상대 경로만 허용되거나 허용 목록과 대조되는가. `config.toml`의 리디렉트 허용 목록이 운영 주소에 `**`를 넓게 걸지 않았는가. 세션 갱신 프록시가 응답을 그대로 돌려주고, 쿠키를 설정하는 응답에 `Cache-Control`을 붙이는가 | 확립 |
| S9 파일 저장소 | 버킷 공개 여부가 의도와 맞는가(개인 파일 = 비공개 + 서명 URL). `storage.objects` 정책이 `bucket_id`와 소유자 폴더로 좁히는가. 공개 버킷에 넓은 SELECT 정책(목록 노출)은 없는가. 업로드에 크기 · 형식 제한 또는 서버 검증이 있는가. 저장 경로 · 파일명을 사용자 입력 그대로 쓰지 않는가 | 확립 |
| S10 개인정보 노출 | 서버에서 화면으로 가는 데이터(클라이언트 컴포넌트 props · 서버 액션 반환값 · 페이지 데이터)에 `select('*')` 전체나 불필요한 개인정보 · 내부 필드가 실리지 않는가. id만 바꿔 남의 행을 읽는 경로가 없는가. `auth.users`를 노출하는 뷰가 없는가 | 확립 |
| S11 비밀값 관리 | `.gitignore`가 `.env*`를 막는가(`.env.example` 제외). 코드 · 설정 · SQL · 문서 · 주석에 키 · 토큰 · 비밀번호 형태 문자열이 없는가(위치만). 키를 `console.log` · URL에 쓰지 않는가 | 확립 |
| S12 남용 방어 | (인증 경로) 가입 · 로그인 · 비밀번호 재설정 · OTP에 반복 시도 방어가 있는가 — Supabase 한도 설정 · CAPTCHA · 자체 제한. (그 밖) 신청 · 메시지 · 메일 발송처럼 비용이나 스팸을 부르는 경로에 호출 횟수 제한이 있는가 | 확립(인증 경로) · 방향성(그 밖) |
| S13 외부 호출 경로 | 예약 작업(`vercel.json` crons) · 웹훅 · Edge Function이 호출자를 인증하는가(`CRON_SECRET` 비교 · 공급자 서명 검증). `verify_jwt = false`인 함수는 안에서 직접 인증하는가. 이런 경로가 service_role 클라이언트를 쓰면 S3 · S4를 함께 본다. 호스팅을 파일로 모르면 자료 부족 | 확립 |
| S14 의존성 | `package.json`의 `next` · `react` · `@supabase/*` 버전과 락파일 유무를 적는다. 알려진 취약 여부는 판정하지 않는다(조회에 네트워크 필요) → "미실측". 공개된 수정 버전과의 대조는 사람이 한다 | 확립(기준) · 미실측 |
| S15 요청 위조(CSRF) | 쿠키 인증을 쓰는 `route.ts`(POST/PUT/DELETE)에 출처(Origin) 확인이나 토큰이 있는가. 상태를 바꾸는 GET 핸들러는 없는가. `serverActions.allowedOrigins`를 넓게 열지 않았는가(49항 1-11) | 확립 |
| S16 서버 대신 요청(SSRF) | 서버 코드가 사용자 입력 URL로 `fetch`하는 곳(링크 미리보기 · 이미지 가져오기 · 웹훅 URL 등록)이 있는가. 있으면 허용 도메인 목록 · 리디렉트 추적 끔 · 내부 주소 차단이 있는가. 없으면 해당 없음(49항 1-12) | 확립 |
| S17 코드 · 명령 · 경로 삽입 | `eval` · `new Function` · `child_process`가 있는가. 사용자 입력으로 만든 파일 시스템 경로 · 저장소 객체 경로가 있는가. 있으면 허용 목록 · 정규화를 거치는가(49항 1-2 · 1-3 · 1-5) | 확립 |
| S18 오류 메시지 노출 | 서버 액션 · route가 DB 오류 · 스택 · 내부 메시지를 응답에 그대로 싣지 않는가. 처리되지 않은 오류의 최후 처리기(`error.tsx` 등)가 있는가(49항 4-1~4-3) | 확립 |
| S19 요청 간 데이터 섞임 | 서버 모듈 전역 변수 · 캐시(전역 Supabase 클라이언트 · `unstable_cache` · 정적 생성)에 사용자별 데이터나 세션이 담기지 않는가(49항 6-1) | 확립(Supabase 캐시 경고) · 추정(코드 패턴) |
| S20 남은 디버그 코드 | 시험용 · 디버그 route/페이지 · 인증 우회 플래그 · 개인정보를 찍는 `console.log` · 주석 속 접속 정보가 운영 코드에 남아 있지 않은가(49항 6-2 · 2-13) | 확립 |

해당 기능이 있을 때만 추가로 볼 것(49항): 중요정보 암호화(2-5) · 토큰을 `Math.random`으로 만들기(2-8) · 약한 비밀번호 허용(2-9) · 선착순 · 포인트 처리의 경쟁 조건(3-1 — 개발 설계 D4와 함께).

이 렌즈가 판단하지 못하는 것: 운영 DB의 실제 정책 상태(대시보드에서 만든 테이블 · 정책 · 버킷은 파일에 없음), Supabase 대시보드 설정(리디렉트 허용 목록 · CAPTCHA · 인증 한도 · 유출 비밀번호 차단), 배포 환경의 실제 환경 변수, git 이력 속 과거 비밀값, 의존성 취약 여부, 침투 시험 · 런타임 동작, 보안 헤더 · CSP · CORS, 개인정보 보호법상 안전성 확보조치의 법적 판단.
