# 렌즈: 개발 설계 (약자 D) v0.2

> 시험 상태: v0.1은 정답이 있는 비교 시험 1회(2026-10-01). **v0.2(D9 분리 · D15~D18 추가 · 근거 보강)는 정답 시험 없음** — 비공개 실제 프로젝트 1회 검토에서 출력 형식 · 안전 규칙이 지켜진 것만 확인했다(2026-10-15).
> 근거: 2026-10-15 웹에서 열어 확인한 공식 · 권위 자료 45건(PostgreSQL 18 · Supabase · Next.js · Vercel · 12-Factor · Google SRE · Fowler · OWASP · Stripe · 토스페이먼츠 · AWS) — 항목별 근거와 링크는 `lens-dev-sources.md`. 대부분 도구 회사의 공식 문서이며 독립 연구가 아니다. 열람이 요약 모델을 거쳤으므로 판정에 쓰기 전 원문 대조를 권한다.
> 등급: 확립 = 공식 문서 · 표준 · 법령 / 방향성 = 연구 · 관행 / 추정 = 근거가 약한 것. 보안 렌즈(S)와 겹치는 곳은 항목에 적었다.

| 항목 | 예/아니오로 물을 것 | 등급 |
|---|---|---|
| D1 구조 | 읽기 · 쓰기가 한 가지 방식(서버 전용 데이터 접근 모듈 또는 DB 함수)으로 통일돼 있는가. 같은 규칙(권한 · 검증 · 상태 전이)이 화면 · 서버 · DB 두 곳 이상에 서로 다르게 구현돼 있지 않은가 | 방향성 |
| D2 쓰기 경로의 검증 | 데이터를 바꾸는 경로(서버 액션 · API 라우트 · DB 함수)마다 호출자 확인 · 그 자원에 대한 권한 · 입력 형식 검증이 그 경로 안에서 일어나는가. 서버가 세션 · DB로 알 수 있는 값(사용자 ID · 별명 · 역할 · 가격)을 클라이언트가 보낸 값으로 받아 쓰지 않는가(권한 부분은 S4와 겹침) | 확립 |
| D3 원자성 | 하나의 업무 동작이 여러 표를 바꿀 때 전부 한 DB 함수 · 트랜잭션 안에서 일어나는가(앱에서 호출을 여러 번 나눠 보내지 않는가). 함수 안에서 오류를 잡고 계속 가는 구간(EXCEPTION)이 있다면 그 앞까지의 변경이 남아도 되는가 | 확립(Postgres 동작) · 방향성("호출 여러 번 = 별개 트랜잭션"은 2차 자료) |
| D4 중복 실행 | 같은 요청이 동시에 두 번 오거나 재시도돼도 한 번만 반영되게 DB 안에 장치가 있는가(고유 제약 · 부분 고유 인덱스 · ON CONFLICT · 행 잠금 · 조건부 UPDATE). '읽고 나서 쓰는' 두 단계 사이에 잠금 · 조건이 없는 곳은 없는가. 정원 · 잔액처럼 다른 행을 봐야 하는 규칙을 CHECK 제약에만 맡기지 않았는가 | 확립 |
| D5 오류 처리 | DB · 외부 호출 결과의 `error`를 확인하지 않고 `data`만 쓰는 곳이나 빈 `catch`는 없는가. 예상된 실패(검증 · 중복)는 반환값으로 사용자에게 알리고, 예상 못 한 실패는 오류 화면 · 기록으로 가는가 | 확립(오류 검사) · 방향성(표시 방식) |
| D6 DB 변경 관리 | 스키마 변경이 (a) 순서가 있는 파일로 저장소에 있고 (b) 적용 이력이 한 곳에 남으며 (c) 같은 파일을 다시 실행해도 최신 수정이 되돌아가지 않고 (d) 운영 전에 운영과 분리된 곳에서 먼저 돌린 기록이 있는가 | 확립((a)(b)) · 방향성((c)(d)) |
| D7 삭제 · 탈퇴 · 보존 | 삭제 · 탈퇴 경로가 개인정보가 든 모든 저장 위치(표 · 파일 저장소 · 로그 · 외부 인증 계정)를 목록으로 갖는가. 외래 키 삭제 동작(기본값 NO ACTION = 삭제 거부)이 의도와 맞는가. 법령상 보존할 항목은 나머지와 분리돼 있는가 | 확립(법령 조문은 원문 대조 필요) |
| D8 테스트 전략 | 돈 · 권한 · 삭제 · 신청 같은 핵심 동작과 그 실패 경로(중복 · 권한 없음 · 입력 오류)를 자동으로 돌리는 테스트가 있고 코드 변경 때 실제로 실행되는가(DB 함수는 로컬 DB · pgTAP 등). 기대값을 사람이 명세에서 적었는가(검사 대상 함수의 출력을 기대값으로 재사용하지 않는가) | 방향성(기대값 부분은 추정) |
| D9a 배포 · 환경 | 이전 배포로 되돌리는 절차가 적혀 있는가. 되돌려도 DB 변경 · 환경 변수는 따로 처리해야 함이 반영돼 있는가. 개발과 운영이 분리돼 있는가 | 방향성(Vercel 되돌리기 한계는 확립) |
| D9b 예약 작업 · 웹훅 | 예약 작업 · 웹훅 처리가 (a) 같은 실행이 두 번 와도 결과가 같고 (b) 겹쳐 실행돼도 안전하며 (c) 놓친 실행을 다음에 따라잡고 (d) 실패가 운영자에게 알려지는가(Vercel 크론은 실패해도 재시도하지 않음) | 확립 |
| D10 비밀값 · 설정 | 비밀값이 저장소 · 브라우저 번들(`NEXT_PUBLIC_` · 클라이언트 컴포넌트)에 없는가(값은 보지 않고 위치만). 필수 설정이 없을 때 조용히 엉뚱한 기본값으로 가지 않는가. `NEXT_PUBLIC_` 값이 빌드 시점에 박힌다는 점이 반영돼 있는가(S3 · S11과 겹침) | 확립 |
| D11 성능 · 규모 | 목록 · 관리자 조회에 상한과 정렬 기준이 있는가. 자주 쓰는 WHERE · JOIN · ORDER BY 열에 인덱스가 있는가. 반복문 안에서 항목마다 따로 조회(N+1)하지 않는가 | 방향성(N+1은 추정) |
| D12 관측 | 핵심 쓰기(신청 · 결제 · 삭제 · 권한 변경) 실패가 운영자에게 닿는 경로(알림 또는 정기적으로 보는 기록)가 있는가. 기록에 `error` 전체(힌트 포함)가 남는가. 비밀번호 · 토큰 · 연락처 같은 값은 기록에 없는가 | 방향성 |
| D13 기술 부채 | 자주 바뀌거나 돈 · 권한이 걸린 코드에 같은 규칙의 복제 구현 · 호출되지 않는 코드 · 임시 우회(TODO)가 남아 있는가. 특히 다시 실행하면 최신 수정이 되돌아가는 옛 정의가 실행 가능한 채 있는가 | 방향성 |
| D14 문서와 코드의 일치 | 계획서 · 결정 기록 · 규칙 문서의 '완료 · 적용됨 · 금지' 문장마다 코드 · SQL에서 확인되는 근거(파일 · 줄)가 있는가. 상태 표기가 서로 모순되지 않는가. 대체된 결정에 '대체됨' 표시가 있는가 | 확립(프로젝트 자체 규칙) · 방향성 |
| D15 외부 서비스 호출 | 결제 · 메일 · 문자 등 밖으로 나가는 호출에 시간 제한이 있는가. 재시도하는 곳은 같은 요청을 두 번 보내도 안전한가. 들어오는 웹훅은 이벤트 ID로 중복을 거르고 순서가 뒤바뀌어도 맞는가. 외부 효과(메일 발송 · 결제 승인)와 DB 확정의 순서가 정해져 있고 한쪽만 성공했을 때 상태를 알 수 있는가 | 확립(웹훅 중복 · 순서) · 방향성(시간 제한 · 재시도) |
| D16 백업 · 복원 | 운영 데이터를 되살릴 수단(백업 · 시점 복구 · 직접 덤프)이 있고 보존 기간과 복원 절차가 문서에 있는가. 파일 저장소는 DB 백업과 따로 챙기는가 | 확립(Supabase 제품 사실) — 파일만으로는 대부분 "자료 부족" |
| D17 시간 · 시간대 · 날짜 경계 | 마감 · 만료 · '오늘' 같은 시각 판정이 시간대 포함 타입(`timestamptz`)과 명시한 시간대(KST)로 일관되는가. 예약 작업 시각이 UTC 기준으로 계산돼 있는가 | 확립(저장 · 크론 UTC) · 방향성(KST 경계) |
| D18 화면 데이터 갱신(캐시) | 데이터를 바꾸는 서버 액션 뒤에 해당 화면의 캐시를 갱신하는가. 페이지의 정적 · 캐시 설정이 자주 바뀌는 데이터와 어긋나지 않는가(사용 중인 Next.js 버전의 캐시 모델 확인) | 방향성 |

이 렌즈가 판단하지 못하는 것: 운영 DB의 현재 상태(실제 적용된 SQL · 정책), 동시 요청의 실제 결과(동시 호출 시험 필요), 실제 부하 · 느린 쿼리, 플랫폼 설정과 요금제(백업 · 로그 보존 · 알림), 테스트가 실제로 결함을 잡는지, 외부 서비스 쪽 동작, 법령 적용의 최종 판단, 렌더링해야 보이는 것.
